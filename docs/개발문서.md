## 1. 프로젝트 개요

**devctl**은 라즈베리파이 위에서 동작하는 디바이스 제어 데몬이다. TCP 소켓으로 클라이언트 명령을 수신하고, 동적으로 로드한 공유 라이브러리(.so) 드라이버를 통해 하드웨어를 제어한다.

| 항목 | 내용 |
|------|------|
| 대상 보드 | Raspberry Pi (ARM64) |
| 언어 | C (서버·드라이버·클라이언트), Python (웹 브릿지) |
| 통신 | TCP / JSON (줄바꿈 구분) |
| 제어 대상 | LED, 버저, 조도 센서, 7세그먼트, 카메라 |
| 서비스 관리 | systemd |

## 2. 개발 환경 및 요구사항

### 하드웨어

| 디바이스 | 연결 방식 | 비고 |
|----------|-----------|------|
| LED | GPIO | 단색 |
| 버저 | GPIO (PWM) | 능동 버저 |
| 조도 센서 | I²C / ADC | 밝기 측정 |
| 7세그먼트 | GPIO (시프트 레지스터 또는 직결) | 카운트다운 표시 |
| 카메라 | CSI (libcamera) 또는 USB (V4L2) | |

### 소프트웨어 의존성

| 패키지 | 용도 |
|--------|------|
| `gcc`, `make` | 빌드 |
| `libcamera` / `v4l-utils` | 카메라 드라이버 |
| `cJSON` 또는 자체 구현 | JSON 파싱 |
| `python3`, `websockets` | 웹 브릿지 |
| `systemd` | 서비스 관리 |

## 3. 설계 배경 및 목표

### 왜 동적 로드(.so)인가

하드웨어 구성이 바뀔 때마다 서버 전체를 재빌드·재배포하지 않기 위해 각 디바이스를 독립 공유 라이브러리로 분리했다. 서버는 `device.h`에 정의된 공통 ABI만 알면 되고, 드라이버는 그 인터페이스를 구현하기만 하면 된다. 새 디바이스를 추가할 때 서버 코드를 전혀 건드리지 않아도 된다.

### 왜 멀티쓰레드인가

센서 폴링, 디스플레이 갱신, 버저 패턴 출력, 카메라 스트림은 각각 독립적인 주기로 동작해야 한다. 이를 단일 이벤트 루프에 합치면 타이밍 제어가 복잡해지므로 쓰레드를 분리하고 공유 상태(`state.h`)로 동기화한다.

### 왜 JSON 프로토콜인가

바이너리 프로토콜 대비 디버깅과 확장이 쉽고, 웹 클라이언트(JavaScript)와 CLI 클라이언트가 동일한 형식을 재사용할 수 있다.

## 5. 모듈 상세

### 5.1 서버 코어

#### `main.c` — 데몬화 + 쓰레드 생성

1. `fork()` → 부모 프로세스 종료 → 세션 리더 분리(`setsid`) → 표준 입출력 `/dev/null` 리디렉션으로 데몬화
2. 드라이버 목록을 순회하며 `loader_load()` 호출
3. `pthread_create`로 sensor / display / buzzer / camera 쓰레드 생성
4. `net_listen()`으로 TCP 소켓 바인드 후 accept 루프 진입

#### `loader.c` — 동적 로드

```
loader_load(path)
  └─ dlopen(path, RTLD_NOW)
  └─ dlsym("dev_init"), dlsym("dev_handle"), dlsym("dev_cleanup"), dlsym("dev_name")
  └─ dev_init() 호출
  └─ 드라이버 테이블에 등록
```

서버 종료 시 `loader_unload_all()`이 각 드라이버의 `dev_cleanup()`을 호출한 뒤 `dlclose()`한다.

#### `net.c` — 소켓 I/O

- `accept()` 후 클라이언트 소켓을 전용 핸들러 쓰레드에 넘긴다.
- 수신은 `\n` 단위 라인 버퍼링으로 처리한다. 부분 수신에 대비해 내부 링 버퍼를 유지한다.
- 연결 종료 시 소켓 닫기 및 쓰레드 정리.

#### `proto.c` — JSON 파싱/빌드

- `proto_parse(buf)` → 명령 구조체 반환
- `proto_build(result)` → JSON 문자열 반환 (`\n` 포함)
- 파싱 실패 시 에러 응답 객체를 반환하고 연결은 유지한다.

#### `dispatch.c` — 명령 디스패치

명령의 `"device"` 필드로 드라이버 테이블을 조회해 `dev_handle(cmd)`를 호출한다. 등록되지 않은 디바이스 이름이면 `{"status":"error","msg":"unknown device"}`를 반환한다.

#### `state.c` — 공유 상태 관리

`state.h`에 선언된 전역 구조체에 대한 접근을 뮤텍스로 보호한다. 쓰레드 간 센서값 공유, 카운트다운 값, 버저 패턴 큐를 여기서 관리한다.

---

### 5.2 디바이스 드라이버 (.so)

각 드라이버는 `device.h`의 ABI 4개를 구현한다. 자세한 내용은 [6장](#6-디바이스-드라이버-abi) 참조.

| 파일 | 빌드 결과 | 주요 기능 |
|------|-----------|-----------|
| `led.c` | `libdev_led.so` | GPIO 핀 HIGH/LOW, PWM 밝기 조절 |
| `buzzer.c` | `libdev_buzzer.so` | 주파수·듀티사이클 설정, 패턴 재생 |
| `light.c` | `libdev_light.so` | 조도값 읽기 (I²C 또는 ADC) |
| `seg.c` | `libdev_seg.so` | 숫자 0–9 표시, 블링크 |
| `cam.c` | `libdev_cam.so` | 스냅샷 캡처, 스트림 시작/중지 |

---

### 5.3 쓰레드 모델

| 쓰레드 | 주기 | 역할 |
|--------|------|------|
| `sensor_thread` | 500 ms | 조도 센서 폴링 → `state.lux` 갱신 |
| `display_thread` | 1 s | `state.countdown` 값을 7세그에 표시, 0 도달 시 이벤트 발행 |
| `buzzer_thread` | 이벤트 구동 | `state.buzzer_queue`에서 패턴 꺼내 재생 |
| `camera_thread` | 프레임 구동 | 스트림 활성화 중 프레임 캡처 후 공유 버퍼에 기록 |

모든 쓰레드는 `state.running` 플래그가 0으로 바뀌면 루프를 탈출하고 종료한다. 메인 쓰레드는 `SIGTERM` / `SIGINT` 핸들러에서 이 플래그를 내린다.

---

### 5.4 공유 상태 (`state.h`)

```c
typedef struct {
    volatile int  running;       // 서버 동작 플래그
    int           lux;           // 최근 조도값 (lux)
    int           countdown;     // 7세그 카운트다운 값
    BuzzerPattern buzzer_queue[QUEUE_SIZE];
    int           bq_head, bq_tail;
    uint8_t      *cam_frame;     // 최신 카메라 프레임 포인터
    size_t        cam_frame_len;
    pthread_mutex_t lock;
} SharedState;
```

쓰레드 간 경쟁 조건 방지를 위해 `state.lock` 뮤텍스를 획득한 후 읽기·쓰기한다.

---

### 5.5 CLI 클라이언트 (`client.c`)

- 실행 인자: `./client <host> <port>`
- `SIGINT` 핸들러에서 소켓을 정상 종료한다.
- 표준 입력에서 명령을 읽어 JSON으로 직렬화 후 전송, 응답을 수신해 출력한다.
- readline 라이브러리를 사용해 인터랙티브 입력을 지원한다.

---

### 5.6 웹 브릿지 (`bridge.py`)

브라우저는 TCP 소켓을 직접 열 수 없으므로 Python WebSocket 서버를 중계자로 둔다.

```
브라우저 ── WebSocket (ws://localhost:8765) ── bridge.py ── TCP ── devctl 서버
```

- `websockets` 라이브러리 기반, 비동기(`asyncio`) 구현
- 수신한 JSON 텍스트를 그대로 TCP로 전달하고, TCP 응답을 WebSocket으로 릴레이한다.
- 웹 프론트엔드(`app.js`)는 연결·명령 전송·응답 파싱을 담당한다.

## 6. 디바이스 드라이버 ABI

`include/device.h`에 정의된 4개 함수를 모든 드라이버가 구현해야 한다.

```c
// 드라이버 초기화. 성공 시 0, 실패 시 -1 반환.
int dev_init(void);

// 명령 처리. cmd는 파싱된 명령 구조체 포인터.
// 응답 JSON 문자열을 동적 할당해 반환 (호출자가 free).
char *dev_handle(const DevCmd *cmd);

// 드라이버 자원 해제. dlclose 직전에 호출된다.
void dev_cleanup(void);

// 드라이버 식별자 문자열 반환 ("led", "buzzer" 등).
const char *dev_name(void);
```

`DevCmd` 구조체 예:

```c
typedef struct {
    char device[32];   // "led", "buzzer", …
    char action[32];   // "on", "off", "set", …
    char params[256];  // 추가 파라미터 (JSON 객체 문자열)
} DevCmd;
```

새 드라이버를 추가할 때는 위 4개 함수를 구현하고 `make`로 `.so`를 빌드한 뒤, 서버 설정에 경로를 추가하면 된다. 서버 재빌드는 불필요하다.

## 7. JSON 프로토콜

상세 명세는 `docs/API명세.md` 참조. 여기서는 구조만 요약한다.

### 요청 형식

```json
{"device": "led", "action": "on", "params": {"pin": 17}}
```

### 응답 형식

```json
{"status": "ok", "data": {...}}
{"status": "error", "msg": "..."}
```

- 메시지 구분자: `\n` (줄바꿈)
- 인코딩: UTF-8
- 최대 메시지 크기: 4096 bytes

## 8. 빌드 시스템

### Makefile 주요 타겟

| 타겟 | 설명 |
|------|------|
| `all` | 서버, 클라이언트, 모든 `.so` 빌드 |
| `server` | `src/server/*.c` → `bin/devctld` |
| `client` | `src/client/client.c` → `bin/client` |
| `devices` | `src/devices/*.c` → `lib/libdev_*.so` |
| `clean` | 빌드 산출물 제거 |
| `install` | `scripts/install.sh` 실행 |

### 컴파일 플래그

```makefile
CFLAGS  = -Wall -Wextra -O2 -pthread
LDFLAGS = -ldl -lpthread
```

드라이버 `.so` 빌드 시 `-fPIC -shared` 플래그를 추가한다.

## 9. 배포 및 서비스 등록

```bash
make install
```

`install.sh`가 수행하는 작업:

1. `bin/devctld`, `lib/libdev_*.so`를 `/usr/local/lib/devctl/`에 복사
2. `scripts/devctl.service`를 `/etc/systemd/system/`에 복사
3. `systemctl daemon-reload && systemctl enable devctl`

### `devctl.service` 핵심 설정

```ini
[Service]
ExecStart=/usr/local/lib/devctl/devctld
Restart=on-failure
User=pi
```

## 10. 알려진 제약 및 향후 과제

| 구분 | 내용 |
|------|------|
| 보안 | TCP 통신에 인증이 없다. 로컬 네트워크 전용으로 사용할 것. TLS + 토큰 인증 추가 필요. |
| 동시 클라이언트 | 클라이언트당 쓰레드 1개 생성 방식이므로 연결이 많을 때 스케일링이 좋지 않다. epoll 기반 이벤트 루프로 전환 검토. |
| 카메라 | 프레임 공유에 단순 포인터 스왑을 사용해 프레임 유실 가능성이 있다. 더블 버퍼링으로 개선 가능. |
| 웹 브릿지 | `bridge.py`가 단일 프로세스이므로 재시작 정책(`systemd`)을 별도로 설정해야 한다. |
| 설정 파일 | 드라이버 경로, 포트 등이 소스에 하드코딩되어 있다. 외부 설정 파일(`/etc/devctl/config.json`) 도입 검토. |
